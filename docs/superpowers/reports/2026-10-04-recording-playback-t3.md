# T3 录后自动准备实施记录

依据：[主计划 T3](../plans/2026-10-03-recording-playback-mainline.md)。本轮仅推进 T3，保留 T1/T2 及三仓已有工作树。核心实现与自动验证已完成；独立审查发现两项阻断，均已纳入失败→修复→通过回归。生产/设备验收及完整 HDR 正向验收仍待完成。

## 行为

- 新增 `on_record_finished.prepare_playback`，默认关闭，旧配置迁移保持关闭；未改真实配置、运行中的服务或历史库。显式启用后，新录播完成即进入持久 pipeline，并在入队时保存源身份、大小及 mtime 形成的版本快照。只有 T2 目录核验匹配后才运行准备。
- SQLite 准备记录以 `(recording_id, source_version, profile_version)` 去重，保存 queued/running/ready/failed/paused、输出路径、输出身份和失败原因。录播目录以事务性 v1→v2 迁移增加准备证明表，保存来源、规则及完整目标身份；失效证明不会被后台仅按相同大小/mtime 重新信任。重启恢复运行中任务；已提交资产可复用，其他源版本不能复用。显式取消停止自动恢复，服务退出保留可恢复暂停。
- 兼容 H.264/AAC LC 原画直接封装 faststart MP4；MP4 已满足条件时复用原文件并登记主资产。不兼容音频仅转 AAC，保持视频包哈希相同；不兼容视频生成明确的 H.264 Main / SDR / 不超过 1080p30 / AAC 兼容版。复制原画的判定同时检查 profile、level、像素格式、分辨率、帧率、HDR 和音频参数。
- 原画主文件在原录播房间目录；兼容版在 `AppData/media-assets/<recording_id>/<source_version>-<profile_version>/compat.mp4`。派生关联使用 manifest v2，复用 T1 持久发布意图、验证、Sync、不可覆盖硬链接和恢复；v2 不授权删源。只有可信资产与目录提交后才标记 ready。
- 与 JIT HLS / 旧 MP4 转换共用 mediawork 并发预算。开始前核验预计空间和保留空间，运行中周期核验保留空间；不足时取消转换、暂停任务并保源。暂停任务让新任务优先，并按上次尝试时间轮转。
- 活跃录制及录播姬分段路径受保护；源变化、产物同大小同 mtime 替换、路径越界及不可信目标均拒绝复用或覆盖。Web 任务列表显示中文暂停状态、原因、筛选和取消，统计包含暂停任务。

## 本轮决定与影响

1. 沿用现有工作树与持久账本。用户于 2026-10-04 明确要求每次改动完成并验证后主动提交本地 commit；服务端以检查点提交当前已验证版本，范围包含此前未提交的 T1/T2、HLS 修复依赖及本轮 T3。提交同时保存实施记录、主计划和源码指纹；根目录的完整测试日志继续保留。不推送、不部署。
2. 准备开关只影响显式启用后的新录播，不自动开启真实库转换。启用后替代旧 `fix_flv_at_first / convert_to_mp4 / delete_flv_after_convert`，上传后删除也关闭；与自定义命令同时启用时明确拒绝后处理并保源。用户需要理解新开关的优先级，配置注释已说明。
3. 跨目录派生产物 manifest v2 保存绝对来源路径，禁止删源。迁移数据目录后不按同名猜关联，旧路径需重新核验或准备。
4. 录播目录新增事务性 v1→v2 迁移，v1 原表保持不变，录播 ID/统计保留。旧 v1 二进制会拒绝 v2 数据库，后续部署/回滚需要保留旧数据库备份。
